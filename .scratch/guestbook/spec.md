# 미니 방명록

Status: ready-for-agent

## Problem Statement

방문자는 회원가입이나 로그인 같은 절차 없이 가볍게 이름과 메시지를 남기고, 다른 사람들이 남긴 메시지를 보고 싶다. 동시에 자기가 남긴 게시글은 나중에 고치거나 지울 수 있어야 하고, 다른 사람이 자기 게시글을 함부로 고치거나 지워서는 안 된다. 계정이 없으므로 "이 게시글이 내 것"임을 증명할 가벼운 수단이 필요하다.

과제 제출물이므로 화면에서 개발자가 누구인지 바로 확인할 수 있어야 한다.

## Solution

한 페이지짜리 방명록을 만든다. 누구나 이름, 메시지, 게시글 비밀번호를 입력해 게시글을 남기고, 페이지에는 모든 게시글이 최신 작성 순으로 이름, 메시지, 작성 시각("3분 전" 같은 상대 시각)과 함께 표시된다.

각 게시글에는 [수정]과 [삭제] 버튼이 있다. 버튼을 누르면 그 게시글 바로 아래에 인라인 폼이 펼쳐지고, 작성할 때 정한 게시글 비밀번호를 입력해야 요청이 처리된다. 비밀번호가 틀리면 요청은 거부되고, 그 게시글 아래에 이유가 안내된다. 게시글 비밀번호는 해시로만 저장되어 DB가 유출되어도 원문이 드러나지 않는다.

페이지 헤더의 제목 아래에 개발자 이름 "조민규"와 학번 "202204273"이 표시된다.

## User Stories

### 조회

1. 방문자로서, 페이지에 들어가자마자 모든 게시글 목록을 보고 싶다. 그래야 다른 사람들이 무엇을 남겼는지 알 수 있다.
2. 방문자로서, 게시글이 최신 작성 순으로 정렬되어 있기를 원한다. 그래야 가장 최근 소식을 먼저 볼 수 있다.
3. 방문자로서, 각 게시글의 작성자 이름을 보고 싶다. 그래야 누가 남겼는지 알 수 있다.
4. 방문자로서, 각 게시글의 메시지를 줄바꿈이 유지된 채로 보고 싶다. 그래야 작성자가 의도한 모양 그대로 읽을 수 있다.
5. 방문자로서, 각 게시글의 작성 시각을 "방금 전", "N분 전", "N시간 전", "N일 전"처럼 상대 시각으로 보고 싶다. 그래야 얼마나 최근 글인지 직관적으로 알 수 있다.
6. 방문자로서, 7일이 넘은 게시글은 한국 시각 기준 날짜(예: 2026-09-30)로 보고 싶다. 그래야 오래된 글도 언제 쓰였는지 정확히 알 수 있다.
7. 방문자로서, 작성 시각에 마우스를 올리면 한국 시각 기준 전체 시각(예: 2026-09-30 14:05 (KST))을 보고 싶다. 그래야 정확한 시각이 필요할 때 확인할 수 있다.
8. 방문자로서, 페이지를 열어 둔 채로 있어도 상대 시각이 1분마다 저절로 갱신되기를 원한다. 그래야 "방금 전"이 계속 멈춰 있지 않는다.
9. 방문자로서, 수정된 게시글에는 "(수정됨)" 표시가 작게 붙기를 원한다. 그래야 처음 쓰인 내용과 달라졌다는 것을 알 수 있다.
10. 방문자로서, "(수정됨)"에 마우스를 올리면 마지막 수정 시각을 보고 싶다. 그래야 언제 바뀌었는지 알 수 있다.
11. 방문자로서, 게시글을 수정해도 목록에서 그 게시글의 위치가 바뀌지 않기를 원한다. 그래야 정렬이 최초 작성 시각 기준으로 일관되게 유지된다.
12. 방문자로서, 게시글이 하나도 없을 때 빈 목록 대신 안내 문구를 보고 싶다. 그래야 페이지가 고장 난 것이 아니라 아직 게시글이 없다는 것을 알 수 있다.
13. 방문자로서, 헤더에서 개발자 이름 "조민규"와 학번 "202204273"을 보고 싶다. 그래야 누가 만든 방명록인지 알 수 있다.

### 작성

14. 방문자로서, 이름, 메시지, 게시글 비밀번호를 입력해 게시글을 남기고 싶다. 그래야 회원가입 없이도 흔적을 남길 수 있다.
15. 작성자로서, 게시글을 남기면 목록 맨 위에 바로 보이기를 원한다. 그래야 잘 등록되었는지 확인할 수 있다.
16. 작성자로서, 등록에 성공하면 작성 폼이 비워지기를 원한다. 그래야 실수로 같은 게시글을 다시 보내지 않는다.
17. 작성자로서, 이름을 비워 두거나 공백만 입력하면 등록이 거부되고 이유를 보고 싶다. 그래야 무엇을 고쳐야 하는지 알 수 있다.
18. 작성자로서, 메시지를 비워 두거나 공백만 입력하면 등록이 거부되고 이유를 보고 싶다.
19. 작성자로서, 게시글 비밀번호를 비워 두면 등록이 거부되고 이유를 보고 싶다.
20. 작성자로서, 이름이 20자를 넘으면 등록이 거부되고 이유를 보고 싶다.
21. 작성자로서, 메시지가 500자를 넘으면 등록이 거부되고 이유를 보고 싶다.
22. 작성자로서, 게시글 비밀번호가 4자 미만이거나 50자를 넘으면 등록이 거부되고 이유를 보고 싶다.
23. 작성자로서, 등록이 거부되어도 입력하던 이름과 메시지가 지워지지 않기를 원한다. 그래야 처음부터 다시 쓰지 않아도 된다.
24. 작성자로서, 입력 앞뒤의 공백이 자동으로 제거되기를 원한다. 그래야 실수로 들어간 공백 때문에 게시글 모양이 흐트러지지 않는다.
25. 작성자로서, 메시지에 여러 줄을 쓸 수 있기를 원한다. 그래야 긴 인사말도 보기 좋게 남길 수 있다.
26. 작성자로서, 입력 칸에 글자 수 제한이 걸려 있기를 원한다. 그래야 등록하기 전에 너무 길다는 것을 알 수 있다.
27. 작성자로서, 내 게시글 비밀번호가 원문 그대로 저장되지 않기를 원한다. 그래야 DB가 유출되어도 다른 곳에서 쓰는 비밀번호가 드러나지 않는다.
28. 작성자로서, 등록을 누른 뒤 처리가 끝날 때까지 버튼이 비활성화되기를 원한다. 그래야 두 번 눌러 같은 게시글이 중복으로 올라가지 않는다.

### 수정

29. 작성자로서, 내 게시글의 [수정] 버튼을 누르면 그 게시글 아래에 메시지 편집란과 게시글 비밀번호 입력란이 펼쳐지기를 원한다. 그래야 페이지를 옮기지 않고 바로 고칠 수 있다.
30. 작성자로서, 편집란에 기존 메시지가 미리 채워져 있기를 원한다. 그래야 일부만 고칠 수 있다.
31. 작성자로서, 게시글 비밀번호가 맞으면 메시지가 수정되기를 원한다. 그래야 오타나 내용을 바로잡을 수 있다.
32. 작성자로서, 수정에 성공하면 인라인 폼이 닫히고 목록에 바뀐 메시지가 보이기를 원한다.
33. 작성자로서, 수정은 메시지에만 적용되고 이름과 게시글 비밀번호는 바뀌지 않기를 원한다. 그래야 게시글의 주인이 흔들리지 않는다.
34. 방문자로서, 게시글 비밀번호가 틀리면 수정이 거부되고 그 게시글 아래에 "비밀번호가 일치하지 않습니다."라는 안내를 보고 싶다. 그래야 남의 게시글을 고칠 수 없다는 것과 이유를 알 수 있다.
35. 작성자로서, 비밀번호가 틀려 거부되었을 때 수정 중이던 메시지는 그대로 남고 비밀번호 칸만 비워지기를 원한다. 그래야 비밀번호만 다시 입력하면 된다.
36. 작성자로서, 수정할 메시지를 비우거나 500자를 넘기면 수정이 거부되고 이유를 보고 싶다.
37. 작성자로서, 수정 도중 마음이 바뀌면 [취소]로 인라인 폼을 닫고 싶다. 그래야 아무것도 바뀌지 않은 채로 돌아갈 수 있다.
38. 방문자로서, 이미 삭제된 게시글을 수정하려 하면 "이미 삭제되었거나 존재하지 않는 게시글입니다."라는 안내를 보고, 목록이 새로 고쳐지기를 원한다. 그래야 화면이 실제 상태와 맞춰진다.

### 삭제

39. 작성자로서, 내 게시글의 [삭제] 버튼을 누르면 그 게시글 아래에 게시글 비밀번호 입력란이 펼쳐지기를 원한다.
40. 작성자로서, 게시글 비밀번호가 맞으면 추가 확인 없이 게시글이 바로 삭제되기를 원한다. 비밀번호 입력 자체가 확인 단계이기 때문이다.
41. 작성자로서, 삭제된 게시글이 목록에서 곧바로 사라지기를 원한다.
42. 작성자로서, 삭제된 게시글이 복구할 수 없게 완전히 지워지기를 원한다. 그래야 남긴 내용이 어딘가에 계속 남지 않는다.
43. 방문자로서, 게시글 비밀번호가 틀리면 삭제가 거부되고 그 게시글 아래에 "비밀번호가 일치하지 않습니다."라는 안내를 보고 싶다. 그래야 남의 게시글을 지울 수 없다.
44. 방문자로서, 이미 삭제된 게시글을 삭제하려 하면 "이미 삭제되었거나 존재하지 않는 게시글입니다."라는 안내를 보고, 목록이 새로 고쳐지기를 원한다.
45. 작성자로서, 삭제 도중 마음이 바뀌면 [취소]로 인라인 폼을 닫고 싶다.
46. 방문자로서, 한 게시글의 인라인 폼에 뜬 안내가 다른 게시글에 섞이지 않기를 원한다. 그래야 어느 게시글에 대한 안내인지 헷갈리지 않는다.

### 보안

47. 작성자로서, 게시글 목록을 불러올 때 게시글 비밀번호의 해시가 브라우저로 전달되지 않기를 원한다. 그래야 해시를 가져가 무차별 대입 공격을 할 수 없다.
48. 작성자로서, 게시글 비밀번호 비교가 서버에서만 이루어지기를 원한다. 그래야 클라이언트를 조작해 권한 확인을 건너뛸 수 없다.
49. 방문자로서, 메시지에 HTML이나 스크립트를 넣어도 글자 그대로 표시되기를 원한다. 그래야 다른 방문자의 화면에서 스크립트가 실행되지 않는다.

## Implementation Decisions

### 저장소와 스키마

- 저장소는 Neon Postgres다. 이미 설치된 `@neondatabase/serverless` 드라이버와 `DATABASE_URL` 환경 변수를 쓴다. ORM 없이 매개변수화된 SQL을 쓴다.
- 테이블은 하나이고 이름은 `posts`다. 도메인 용어인 **게시글 (Post)**과 맞춘다.
  - `id`: bigint identity 기본 키
  - `name`: text, not null
  - `message`: text, not null
  - `password_hash`: text, not null
  - `created_at`: timestamptz, not null, 기본값 now()
  - `updated_at`: timestamptz, null 허용. 한 번이라도 수정되면 수정 시각을 기록한다.
- 목록 정렬을 위해 `created_at desc` 인덱스를 둔다.
- 스키마는 저장소에 SQL 파일로 두고, npm 스크립트(`db:init`)로 한 번 실행해 적용한다. 앱이 요청을 처리하면서 테이블을 만들지는 않는다.

### 게시글 비밀번호 (ADR-0001)

- 원문을 저장하지 않는다. `password_hash` 컬럼 하나에 `scrypt$<salt hex>$<hash hex>` 형식으로 저장한다.
- salt는 게시글마다 `node:crypto`의 `randomBytes(16)`로 새로 만든다. hash는 `scrypt(비밀번호, salt, 64)`로 만든다.
- 비교는 `timingSafeEqual`로 한다. 추가 의존성은 없다.
- 형식 앞부분(`scrypt$`)으로 알고리즘을 구분할 수 있게 해 둔다. 저장된 값의 형식을 해석할 수 없으면 비밀번호 불일치로 취급한다.

### 게시글 모듈 (단일 테스트 경계)

게시글에 관한 모든 규칙을 담는 깊은 모듈 하나를 둔다. 입력 검증, 해시 생성과 비교, SQL은 전부 이 모듈 안에 숨기고, 밖으로는 아래 네 함수만 드러낸다.

- `listPosts()`: 모든 게시글을 `created_at` 최신순으로 돌려준다. 각 게시글은 `id`, `name`, `message`, `createdAt`, `updatedAt`(수정된 적이 없으면 null)으로 이루어진다. `password_hash`는 쿼리에서 SELECT하지 않는다.
- `createPost({ name, message, password })`
- `updatePostMessage({ id, message, password })`
- `deletePost({ id, password })`

작성·수정·삭제 세 함수는 예외를 던지는 대신 아래 결과 중 하나를 돌려준다.

- `{ ok: true }`: 성공
- `{ ok: false, reason: "invalid", fieldErrors }`: 입력 검증 실패. `fieldErrors`는 필드 이름(`name`, `message`, `password`)별 안내 문구다.
- `{ ok: false, reason: "wrong-password" }`: 게시글 비밀번호 불일치 (수정·삭제만 해당)
- `{ ok: false, reason: "not-found" }`: 해당 id의 게시글이 없음 (수정·삭제만 해당)

DB 연결 실패처럼 예상하지 못한 오류는 결과로 감싸지 않고 예외로 흘려보낸다.

### 입력 검증 규칙 (게시글 모듈 안)

- 모든 문자열 입력은 앞뒤 공백을 제거한 뒤 검증한다. 저장도 공백을 제거한 값으로 한다.
- 이름: 1–20자
- 메시지: 1–500자, 줄바꿈 허용
- 게시글 비밀번호: 4–50자. 비밀번호는 공백을 제거하지 않는다. 사용자가 공백을 포함해 정했다면 그대로 존중한다.
- 글자 수는 JavaScript 문자열 길이가 아니라 사용자가 보는 문자 단위로 센다. 한글과 이모지가 섞여도 제한이 직관적으로 동작하게 하기 위해서다.
- 수정·삭제의 `id`가 올바른 정수가 아니면 `not-found`로 취급한다.

### 수정·삭제 처리 순서 (게시글 모듈 안)

1. id로 `password_hash`만 조회한다. 행이 없으면 `not-found`를 돌려준다.
2. 입력된 게시글 비밀번호를 저장된 salt로 해시해 비교한다. 일치하지 않으면 `wrong-password`를 돌려준다.
3. 일치하면 실행한다.
   - 수정: `message`와 `updated_at = now()`를 갱신한다.
   - 삭제: 행을 완전히 삭제한다.
   - 1단계와 3단계 사이에 게시글이 삭제되었다면, 영향받은 행이 0이므로 `not-found`를 돌려준다.
4. 수정의 입력 검증은 1단계보다 먼저 한다. 잘못된 메시지로는 DB에 접근하지 않는다.

### 서버 처리 층

- 목록 페이지는 서버 컴포넌트이며, 게시글 모듈의 `listPosts()`를 직접 호출한다. 목록은 요청마다 새로 읽는다. 게시글은 자주 바뀌므로 정적으로 캐시하지 않는다.
- 작성·수정·삭제는 Server Actions로 처리한다. Server Action은 FormData에서 값을 꺼내 게시글 모듈을 호출하고, 결과를 화면 상태로 바꿔 주는 얇은 층이다. 이 층에 비즈니스 규칙을 두지 않는다.
- 결과를 화면 안내로 바꾸는 규칙:
  - `wrong-password`: "비밀번호가 일치하지 않습니다."
  - `not-found`: "이미 삭제되었거나 존재하지 않는 게시글입니다." 그리고 목록 경로를 재검증해 새로 고친다.
  - `invalid`: 필드별 안내를 해당 입력칸 아래에 표시한다.
  - `ok`: 목록 경로를 재검증한다.
- 폼 상태와 안내 문구는 `useActionState`로 관리한다. 제출 중에는 버튼을 비활성화한다.
- Next.js 16은 API와 관례가 이전 버전과 다를 수 있다. 구현하기 전에 프로젝트에 포함된 Next.js 문서에서 Server Actions, `useActionState`, 재검증, 동적 렌더링 방식을 확인한다.

### 화면 구성

- 한 페이지 구성이다: 헤더 → 작성 폼 → 게시글 목록.
- 헤더: 방명록 제목, 그 아래 "조민규 · 202204273".
- 작성 폼: 이름, 메시지(여러 줄), 게시글 비밀번호(가려진 입력) 칸과 등록 버튼.
  - 클라이언트 쪽에는 `required`와 `maxLength`만 둔다. 최종 검증은 서버가 한다.
  - 성공하면 폼을 비운다. 실패하면 입력값을 유지한다.
- 게시글 항목: 이름, 메시지(줄바꿈 유지), 상대 시각, 수정되었으면 "(수정됨)", [수정]과 [삭제] 버튼.
- 인라인 폼: 게시글마다 독립된 클라이언트 컴포넌트다. 한 번에 한 모드(수정 또는 삭제)만 펼친다.
  - 수정 모드: 기존 메시지가 채워진 편집란, 게시글 비밀번호 칸, [저장], [취소]
  - 삭제 모드: 게시글 비밀번호 칸, [삭제 확인], [취소]
  - 성공하면 폼을 닫는다. `wrong-password`이면 비밀번호 칸만 비우고 편집 중이던 메시지는 유지한다.
- 게시글이 없으면 "아직 게시글이 없습니다. 첫 게시글을 남겨 보세요." 같은 안내를 표시한다.
- 메시지는 React의 기본 텍스트 출력만으로 표시해 HTML로 해석되지 않게 한다.
- 스타일은 이미 설치된 Tailwind CSS v4로 만든다.
- 화면 문구는 모두 "게시글" 용어를 쓴다. "글"만 단독으로 쓰지 않는다.

### 상대 시각 (별도 순수 함수)

- `formatRelativeTime(date, now)`는 순수 함수다. 두 시각을 받아 표시 문자열을 돌려주고, 현재 시각을 스스로 읽지 않는다.
  - 1분 미만: "방금 전"
  - 60분 미만: "N분 전"
  - 24시간 미만: "N시간 전"
  - 7일 미만: "N일 전"
  - 그 이상: Asia/Seoul 기준 날짜 `YYYY-MM-DD`
  - N은 버림으로 계산한다. 예를 들어 59분 59초는 "59분 전"이다.
  - `date`가 `now`보다 미래이면(서버와 브라우저의 시계 차이) "방금 전"으로 표시한다.
- 전체 시각 툴팁에 쓸 Asia/Seoul 기준 `YYYY-MM-DD HH:mm (KST)` 포맷도 같은 곳에 둔다. 서버와 브라우저의 시간대와 관계없이 항상 KST로 표시해야 한다.
- 시각 표시는 작은 클라이언트 컴포넌트가 담당한다. 이 컴포넌트는 `formatRelativeTime`을 호출하고, 1분마다 `now`를 갱신하며, 전체 시각을 `title`로 붙인다.
- 서버 렌더링과 브라우저의 첫 렌더링 사이에 시각이 달라서 hydration 불일치가 나지 않도록 처리한다. 방법은 예컨대 마운트한 뒤에 상대 시각을 계산하고, 그 전에는 KST 전체 시각을 표시하는 것이다.
- "(수정됨)" 표시에도 같은 방식으로 수정 시각 툴팁을 붙인다.

## Testing Decisions

- **이번 범위에서는 테스트 코드를 작성하지 않는다.** 합의 단계에서 범위 제외로 정했다. 아래는 나중에 테스트를 붙일 때 따를 경계와 원칙이다. 구현은 이 경계를 지켜서 테스트를 붙이기 쉬운 구조로 만든다.
- 좋은 테스트는 공개 인터페이스의 외부 동작만 확인한다. 해시 문자열의 모양, SQL 문장, 내부 헬퍼 호출 여부 같은 구현 세부 사항은 확인하지 않는다.
- **주 경계: 게시글 모듈.** 네 함수와 결과 값만 관찰한다. 확인할 시나리오는 다음과 같다.
  - 작성한 게시글이 목록 맨 위에 나온다.
  - 목록 결과에 게시글 비밀번호나 그 해시가 포함되지 않는다.
  - 올바른 비밀번호로 수정하면 메시지와 `updatedAt`이 바뀌고, 목록 순서는 그대로다.
  - 틀린 비밀번호로 수정·삭제하면 `wrong-password`가 나오고, 게시글은 바뀌지 않는다.
  - 없는 id로 수정·삭제하면 `not-found`가 나온다.
  - 이미 삭제한 게시글을 다시 삭제하면 `not-found`가 나온다.
  - 각 길이 경계값(0, 1, 20, 21자 등)과 공백만 있는 입력의 `invalid` 결과
  - 같은 비밀번호로 만든 두 게시글이 서로 다른 해시를 갖는지는 저장된 값을 직접 봐야 확인할 수 있다. 이것은 구현 세부 사항이므로 테스트하지 않는다.
  - 테스트는 실제 Postgres(별도의 테스트용 Neon 브랜치나 로컬 Postgres)를 대상으로 하는 통합 테스트를 권장한다.
- **보조 경계: `formatRelativeTime(date, now)`.** 순수 함수이므로 고정된 `now`로 각 구간의 경계값을 확인한다.
  - 59초, 60초, 59분 59초, 60분, 23시간 59분, 24시간, 6일 23시간, 7일
  - 미래 시각
  - KST 날짜 경계: UTC 기준으로는 전날이지만 KST 기준으로는 다음 날인 시각
- 저장소에 기존 테스트나 선례는 없다. create-next-app 초기 상태다. 테스트를 붙인다면 Vitest를 권장한다.

## Out of Scope

- 회원가입, 로그인, 계정
- 관리자 기능 (다른 사람의 게시글을 강제로 삭제하는 권한 등)
- 게시글 비밀번호 찾기 또는 재설정
- 이름이나 게시글 비밀번호의 수정. 수정할 수 있는 것은 메시지뿐이다.
- 삭제한 게시글의 복구 (soft delete 없음)
- 페이지네이션이나 무한 스크롤. 전체 목록을 한 번에 표시한다.
- 스팸 방지, 캡차, 요청 제한(rate limit), 비밀번호 무차별 대입 방어
- 실시간 갱신. 다른 사람의 새 게시글은 새로 고쳐야 보인다. 상대 시각 표시는 1분마다 갱신된다.
- 자동화 테스트 코드
- 배포 설정

## Further Notes

- 용어는 [GLOSSARY.md](../../GLOSSARY.md)를 따른다. 방명록의 한 건은 **게시글 (Post)**, 비밀번호는 **게시글 비밀번호**다. 코드에서도 `Post`를 쓰고 `Entry`는 쓰지 않는다.
- 게시글 비밀번호 저장 방식의 배경과 버린 대안은 [ADR-0001](../../docs/adr/0001-게시글-비밀번호-scrypt-해시.md)에 있다. 평문 저장으로 되돌리지 않는다.
- `DATABASE_URL`은 `.env.local`에만 두고 커밋하지 않는다. `.gitignore`가 이미 `.env*`를 제외하고 있다.
- 비밀번호 비교는 시간 차이 공격을 막기 위해 `timingSafeEqual`로 하지만, `not-found`와 `wrong-password`를 구분해 안내하는 이상 게시글이 존재하는지는 알 수 있다. id가 목록에 공개되어 있으므로 이것은 받아들인 트레이드오프다.
